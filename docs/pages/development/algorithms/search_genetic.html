Algorithms - Genetic Algorithm

The OSTRICH genetic optimization algorithms

Initial Publication:

April 11, 2021

Modified:

April 11, 2021

The following optional group will configure either the binary- or real-coded genetic algorithm and will be processed if [ProgramType] is set to “BinaryGeneticAlgorithm” (i.e. BGA) or “GeneticAlgorithm” (i.e. RGA). 

BeginGeneticAlg
PopulationSize       [pop_size]
MutationRate         [mut_rate]
CrossoverRate        [xover_rate]
Survivors            [nelites]
NumGenerations       [numgens]
InitPopulationMethod [imethod]
ConvergenceVal       [conv_val]
EndGeneticAlg

BeginGeneticAlg
PopulationSize       50
MutationRate         0.05
CrossoverRate        0.90
Survivors            1
NumGenerations       10
InitPopulationMethod random
ConvergenceVal       1.00E-4
EndGeneticAlg

Figure 1: General Format (left) and Example (right) of the Genetic Algorithm Group

Where BeginGeneticAlg and EndGeneticAlg are parsing tags that wrap a set of algorithm configuration variables. These variables are described below:

  • InitPopulationMethod: This variable controls how the algorithm configures the initial population of candidate solutions. Supported values are: “random”, “LHS” (Latin Hypercube Sampling), and “QuadTree”. The default value is “random”.
  • PopulationSize: The population size. The default value is 50.
  • MutationRate: The mutation rate for child members. The default value is 0.05 (i.e. 5%).
  • CrossoverRate: The probability that two randomly chosen population members will be crossed over (combined at a random parameter position) when generating the next generation. The default value is 0.90 (i.e. 90%).
  • Survivors: The number of elites who pass unchanged to next generation. The default value is 1.
  • NumGenerations: The number of generations in the search algorithm. The default value is 10.
  • ConvergenceVal: This is the convergence value for the algorithm. If the relative difference between the current minimum and the median of the latest generation is less than or equal to this value, the algorithm will halt. The default value is 1.00E-4.

Warm Start

The genetic algorithm supports an optional “warm start” capability that allows a previous, and possibly incomplete or interrupted, GA search to be resumed rather than restarted from the beginning. Warm starting is enabled by adding the OstrichWarmStart keyword to the top level of the OSTRICH input file (i.e. outside of, and in addition to, the BeginGeneticAlg/EndGeneticAlg group), as shown in Figure 2. 

OstrichWarmStart [yes/no]

OstrichWarmStart yes

Figure 2: General Format (left) and Example (right) of the Warm Start Keyword

When warm starting is active, OSTRICH will not delete the OstOutput0.txt file or the per-processor OstModelN.txt files (where N is the processor id) left over from a previous run. These files record every model evaluation performed by the previous run and must remain in the run directory for a warm start to succeed. Before launching the search, OSTRICH pre-processes these files to:

  • Determine how many generations were completed by the previous run, based on the contents of OstOutput0.txt.
  • Recover previously evaluated parameter sets and objective function values from each processor's OstModelN.txt file, and identify the best solution found so far.
  • Reconstruct the population for the generation that was in progress when the previous run ended, reusing already-evaluated parameter sets instead of re-evaluating them. Any remaining members needed to complete the population are generated using the standard genetic algorithm operators, or at random if too few prior evaluations are available to do so.
  • Repopulate the model evaluation cache with the recovered evaluations so that previously solved parameter sets are not needlessly re-run.

The search then resumes from the recovered generation count and continues until the NumGenerations or ConvergenceVal criteria (described above) are satisfied. Since the recovered state is matched up against the current run's configuration and processor count, a warm started run should use the same PopulationSize and the same number of processors as the run being resumed.
